# kreitz-webdev

Nx monorepo, npm only (`package-lock.json`; no `packageManager` field, no other lockfile). Apps: `api` (NestJS + Prisma/Postgres + Redis), `frontend` (Angular), `portal` (Angular). No `libs/`/`packages/` yet.

`api` serves multi-tenant website/project management for a CMS user (Better Auth session, email/password + GitHub OAuth) plus a public, website-token-authenticated read API for published projects. GitHub repos can be imported as projects for a user with a linked GitHub account.

## Commands

- Full list lives in root `package.json` scripts — check there before guessing a flag.
- Typecheck: `npm run typecheck` (runs `nx run-many --target=tsc --all` — the target is `tsc`, not `typecheck`).
- Prisma: use the `npm run prisma:*` scripts (`prisma:generate`, `prisma:migrate`, `prisma:studio`, `prisma:reset`) — they load `.env.local` and pass `--config apps/api/prisma.config.ts`. Raw `npx prisma ...` misses both.
- Format: `npm run format` / `format:check` — root Prettier scripts, not an Nx target (the only exception to "always run tasks through nx" below).
- Copy `.env.example` to `.env.local` before `npm install` — `postinstall` runs `prisma generate` against it.

## Gotchas

- `apps/api/prisma/schema.prisma` is generated by `npm run auth:generate` (better-auth CLI, config at `apps/api/src/core/auth/auth-cli.config.ts`) — regenerate through that script instead of hand-editing the auth models.
- Every `apps/api` HTTP response is wrapped in a `{statusCode, message, data}` envelope — see `.claude/rules/nestjs-module-structure.md` for the mechanism and how to opt out.
- `apps/api`'s `REDIS_URL` is required, not optional — Redis backs Better Auth's session/rate-limit storage and is mandatory infra, not a degradable cache.

## Architecture & Code Quality (hard rules)

Hard rules live under `.claude/rules/` (path-scoped, loaded on demand):

- `.claude/rules/typescript-style.md` — repo-wide TS/engineering rules (explicit access modifiers, no speculative patterns, DI over singletons, zero comments, etc.)
- `.claude/rules/nestjs-module-structure.md` — `apps/api` module structure, barrels, DI tokens, dependency direction, DTOs own their own mapping, response envelope, atomic repository writes, no duplicated helpers, testing convention
- `.claude/rules/nestjs-logging.md` — `apps/api` `PinoLogger` conventions: injection pattern, log levels, event naming, secret-safety
- `.claude/rules/security.md` — `apps/api` auth scheme, rate limiting, validation, CORS/proxy trust, secrets
- `.claude/rules/testing.md` — `apps/api` mocking convention, e2e status, `PinoLogger`/DI mocking patterns
- `.claude/rules/nestjs-patterns.md` — `apps/api` lifecycle hooks, injection scopes, DI token/scope interaction
- `.claude/rules/angular-components.md` — `apps/frontend`/`apps/portal` smart/presentational component split

Invoke the matching skill instead of guessing:

- `typescript-expert` — type-level design questions, generics, monorepo TS config, migration issues.
- `nestjs-expert` / `nestjs-best-practices` — module/DI structure, decorators, guards/interceptors/pipes, Nest architecture decisions.
- `nodejs-best-practices` — framework/async/security/deployment decisions outside Nest's own conventions.
- `clean-code` — naming, function size/shape, and general readability review or refactor passes.

Invoke the matching `.claude/agents/` subagent instead of doing it inline:

- `code-quality-reviewer` — after any non-trivial `apps/api` change, check the diff against the rules above before considering the work done. Read-only, never fixes.
- `api-designer` — scaffold a new REST endpoint (controller route, DTO, Swagger).
- `test-writer` — generate Jest specs for existing code, following the established mocking convention.
- `db-migration` — a `schema.prisma` change and its migration.
- `backend-specialist` — a multi-file NestJS module/DI refactor, not a new-endpoint scaffold.

## General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), ALWAYS invoke the `nx-generate` skill FIRST before exploring or calling MCP tools

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill handles generator discovery internally - don't call nx_docs just to look up generator syntax
