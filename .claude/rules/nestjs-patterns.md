# NestJS lifecycle & provider scopes (apps/api)

- **`OnModuleInit`/`OnModuleDestroy` are used only where a real external connection needs explicit open/close** — `RedisService` (`apps/api/src/database/redis/redis.service.ts:7,23-30`: `onModuleInit` pings and logs, `onModuleDestroy` calls `client.quit()`) and `PrismaService` (`apps/api/src/database/prisma/prisma.service.ts:8,21-28`: `$connect()`/`$disconnect()`). `CacheService` (`apps/api/src/database/cache/cache.service.ts:9,33-35`) implements only `OnModuleDestroy` (`cache.disconnect()`) — its underlying store connects lazily/non-blocking (`Cacheable({ ..., nonBlocking: true })`), so there's nothing to await in `onModuleInit`. Don't add `OnModuleInit` to a service just for symmetry; add it only when there's an actual connect/warm-up step to run and await.
- **`OnApplicationBootstrap`/`OnApplicationShutdown` are not used anywhere in this repo.** Don't introduce them without a concrete need those two module hooks above don't already cover (e.g. work that must run after *all* modules have initialized, not just this one).
- **Shutdown hooks only fire because `app.enableShutdownHooks()` is called** (`apps/api/src/bootstrap/app.boostrap.ts:41`) — this is what wires OS signals to `OnModuleDestroy`. If a future bootstrap path (e.g. a serverless/lambda entrypoint) skips this call, `RedisService`/`PrismaService`/`CacheService` cleanup won't run; don't assume it's automatic.
- **Every provider is default (singleton) scope — zero `Scope.REQUEST`/`Scope.TRANSIENT` anywhere in `apps/api`.** This is deliberate, not a gap: per-request data is carried on the `Request` object itself, not on provider instances — `WebsiteTokenGuard` sets `request.websiteId`/`request.websiteTokenId` after validating a token (`apps/api/src/common/guards/website-token.guard.ts:95-96`), and `ArcjetRateLimitGuard` reads `request.websiteId` back off the same request in a later guard (`apps/api/src/common/guards/arcjet-rate-limit.guard.ts:44`). Follow that pattern (attach to `Request`, read it back downstream) instead of reaching for `Scope.REQUEST` to give a provider per-request state — request-scoped providers rebuild the whole DI subtree per request and this repo has never needed that cost.
- **Token-bound providers are singletons too.** Repository interface tokens (`@Inject(WEBSITE_TOKEN_REPOSITORY)` etc., `apps/api/src/common/guards/website-token.guard.ts:22-32`) and `registerAs` config tokens (`@Inject(appConfig.KEY)`, `arcjet-rate-limit.guard.ts:28`; `@Inject(redisConfig.KEY)`, `redis.service.ts:11`) bind to providers that inherit default scope like any class provider — a guard or service holding one has no per-request lifecycle of its own just because it was injected by token. Don't add a scope to a token registration to get "fresh" per-request state; attach it to `Request` instead, per the point above.
