# Logging conventions (apps/api)

- **Always `PinoLogger`, never Nest's static `Logger` or `console.*`.** Constructor-inject `PinoLogger` and call `.setContext(ClassName.name)` in the constructor body — this is the only logging mechanism in this codebase; a service reaching for `new Logger(...)` or `console.log` is reimplementing something that already exists and bypasses Pino's structured/redaction pipeline.
- **`info` for routine mutations, `warn` for rejections and security-relevant events.** Every `create`/`update`/`delete` on a service logs an `info` event on success. Every `NotFoundException`/`ConflictException`/`ForbiddenException`/`UnauthorizedException` thrown for an authorization or ownership check logs a `warn` immediately before the throw. `LOG_LEVEL` defaults to `debug` in development and `warn` in production (`apps/api/src/config/app.config.ts`), so `info` logs are dev-only visibility while `warn` logs are the ones that actually reach production log aggregation — don't log routine success at `warn` (noise) or a real rejection at `info` (invisible in prod).
- **Structured `event` field, `module.action` / `module.rejected` naming.** Every log call passes a single object with an `event: 'module_name.action'` field (snake_case module name, dot-separated action) plus relevant ids (`userId`, `websiteId`, `projectId`, etc.) — never a bare interpolated string. Keep the event name scoped to the module/concern that actually owns the log call, not the module it happens to be adjacent to (a generic rate-limit guard's event should be `rate_limit.denied` / `arcjet.*`, not borrow `website_token.*` just because that's the endpoint it's currently guarding).
- **Never log a secret.** No token, token hash, session cookie, password, or OAuth access/refresh token in any log call — not directly, not via an interpolated URL/HTML body that embeds one, not via logging a raw `error` object that might carry one in its message/cause chain. When in doubt, log only ids and a `reason` string, never the raw value that triggered the log.
- **Request correlation is already wired — don't rebuild it.** Every request gets a request id (`apps/api/src/core/logging/request-id.middleware.ts`, `AsyncLocalStorage`-based, `getRequestId()` helper), attached to every Pino log line for that request automatically and exposed as the `x-request-id` response header. Nothing in application code needs to pass or attach it manually.
