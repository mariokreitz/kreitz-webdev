# NestJS module structure (apps/api)

- **Every feature module exposes a public barrel (`index.ts`).** Code outside the module imports only from that barrel, never from the module's internal files directly.
- **Only Nest's own module-wiring files live at a module's top level** (`*.module.ts`, `*.service.ts`, `*.controller.ts`, and other framework-recognized artifacts — middleware, guard, interceptor, pipe). Everything else gets its own subfolder — `types/`, `interfaces/`, `strategies/`, `dto/`, `tokens/` (DI injection tokens), `constants/` (defaults/fallbacks) — re-exported through the module's `index.ts` barrel. Only add the subfolders a module actually needs; don't scaffold empty ones.
  - Example shape: `website-token.module.ts`, `website-token.service.ts`, `website-token.controller.ts`, `index.ts`, plus `dto/`, `tokens/`, `utils/`, `__tests__/` as needed (see `apps/api/src/modules/website-token/`).
  - Watch for circular injection: a file inside one of those subfolders must import sibling files/subfolders directly, never back through the module's own `index.ts` — that's an import cycle into itself.
  - Keep DI tokens in `tokens/*.tokens.ts` (one file per module, e.g. `tokens/website-token.tokens.ts`) so both the module and its subfolder files can import them without routing through the barrel. `constants/` is for actual default/fallback values, a distinct concern — don't conflate the two subfolders.
- **Dependency direction between modules is one-way and explicit.** A module that depends on another injects that module's exported service via its barrel (`@app/modules/x`), never reaches past the barrel into a sibling module's internals. When importing the barrel itself would create a real circular module-load (not just circular data dependency) — e.g. `website.service.ts` needs `website-domain`'s `normalizeDomain`, but `website-domain.module.ts` also imports `WebsiteModule` for ownership checks — import the specific leaf file directly (`@app/modules/website-domain/utils/normalize-domain`) instead of the barrel, and leave a one-line WHY comment explaining it's deliberate, not an oversight. This is a narrow, documented exception, not a license to bypass barrels generally.
- **Cross-cutting modules used repo-wide are `@Global()` + listed in the owning module's `exports`**, matching `PrismaModule`/`RedisModule`. Don't mark a module `@Global()`/export it if it has nothing to export — that's dead config, delete it.
- **Redaction/serialization of sensitive data uses an allow-list, not a deny-list.** Explicitly list the fields to keep; a field never included can't leak via a redact path someone forgets to update.
- **One owner per cross-cutting concern.** Don't let two mechanisms register the same middleware/interceptor/logging path — pick one registration site.
- **Tests follow the `__tests__`-per-feature convention**, not colocated `*.spec.ts`. Redaction/sanitization logic and other pure functions must ship with tests, not be deferred.
- **DTOs own their own mapping.** A response DTO/type gets a `static fromRecord(record: XRecord): XDto` (or `fromRecordAndSecret`/`fromApiResponse` when the shape genuinely needs more than one source) that does the field-by-field mapping — services and repositories never hand-map a record into a response shape inline or in a private method. Every module must have a real response DTO; returning a raw Prisma-shaped repository record straight through a controller is not acceptable, even for "internal" fields that aren't obviously sensitive (`website.controller.ts` leaked `userId` this way before this rule existed).
- **Every response wraps in a `{statusCode, message, data}` envelope** via the global `ResponseInterceptor` (`apps/api/src/common/interceptors/response.interceptor.ts`) and matching `GlobalExceptionFilter` for errors (`data: null`). Use `@ResponseMessage('...')` for a custom message (default `'Success'`); use `@SkipResponseEnvelope()` only when a route's response shape is genuinely constrained by something else (e.g. Terminus health checks, which k8s probes parse in their raw format).
- **Repository writes on an owner-scoped resource are atomic**, not check-then-act. Use `updateMany`/`deleteMany` with a compound `where: { id, <ownerId> }` and check `result.count` to distinguish not-found from success — never a `findFirst` ownership check followed by a separate `update`/`delete` keyed on bare `id`.
- **A repository whose model has a `@unique` constraint catches the resulting P2002 and re-throws `ConflictException`** (see `apps/api/src/database/utils/unique-violation.ts`) — an app-level pre-check (`findByX` before insert) is fine for the happy path but is not itself race-safe; the DB constraint plus this translation is what actually closes the race.
- **No duplicated helper logic.** If the same normalization/hashing/validation logic is about to be written a second time (even with a plausible-sounding local variation), it isn't — import the existing one. This repo has hit this twice already: hostname normalization and token hashing were each independently reimplemented in a guard instead of importing the canonical module-owned version.
